# ADR 0002: Complete Rust kernel with a pinned Linux contract

Status: **Accepted, 2026-10-25.**
Supersedes ADR 0001's continuing upstream integration/promotion obligations and
its unspecified hardware scope. Other principles of [0001](0001.md) remain.
This decision governs the roadmap and compatibility policy.

## Decision

The priority is a complete Rust kernel for a declared target, followed by the
selected userspace components. Continual convergence with Linux mainline is not
a goal. Preserve behavior at real boundaries; redesign Rust internals deliberately.

### Behavioral baseline

Pin **Linux 6.18.58 LTS**, released 2026-10-21, as the initial behavioral spec.
It is listed by [kernel.org](https://www.kernel.org/) and the 6.18 series has
[projected support through December 2028](https://www.kernel.org/category/releases.html).
Pinned stable commit: `2926d88bb7fc4608fd942453d929c39e4e5ec006`
(tag object `b28ed6cce8167f278fbbae4c8ba25d593fcf1b63`, verified against
the stable repository refs). Verify and record the signed release provenance
during import; never silently follow the moving 6.18 branch.

Compatibility means this baseline's Linux userspace ABI and observable behavior
for the declared configuration: syscalls, ELF, `/proc`, `/sys`, ioctls, ext4 data,
and supported wire protocols. Preserve its upstream compatibility tests and add
missing differential tests. A deliberate behavioral change requires an explicit
contract change and corresponding tests, not silently relaxed expectations.

The current engineering source is `21a7f44fd0765fcc5194130b28767786eba1d1e7`,
not 6.18.58. Existing results stay attributed to it. Prepare the
LTS transition on a separate branch, preserving published history and replaying
project changes with review. Rerun baseline/replacement tests before adopting it;
old test results do not certify the LTS. Any newer Rust infrastructure needed
must be imported as an explicit, inventoried change.

### Upstream and subsystem divergence

Do not merge every upstream release or require mainline parity before promotion.
Review and intentionally port chosen security fixes and important behavior
changes. Track relevance, disposition and regression evidence for selected fixes.
A new behavioral baseline is an occasional explicit decision, not an obligation.

Each subsystem gets a recorded **divergence point**: the reviewed commit at which
it is fully Rust within the declared target. Record its contract, ownership,
remaining external boundaries, tests, and reference C revision. From that point,
its upstream implementation is reference-only and is never merged again. Useful
fixes are understood and reimplemented in Rust. A future whole-tree update must
exclude divergent implementations and cannot silently reset this rule.

Internal kernel APIs, module ABI and C structure layouts are not commitments once
a subsystem is fully Rust. During transition, preserve only the interfaces needed
by remaining callers. Executing C remains unfinished work. Retained reference C
is not execution. Separate translation from redesign, and remove adapters when
Rust owns both sides. Generic abstractions should reuse or engage upstream work
for review, without creating an obligation to track upstream indefinitely.

### Declared completion target

Declare a VM/server target, checked in as resolved architecture configurations:

| Area | Included target |
| --- | --- |
| Architectures | x86_64 and arm64, little-endian, 4 KiB pages, SMP |
| Machines | QEMU q35 (x86_64) and virt (arm64), serial console, generic timers/interrupt controllers |
| Devices | Virtio block and network; PCI transport on x86_64, MMIO transport on arm64; RAM block driver |
| Memory/process core | Virtual memory, page allocation, faults, mmap, process/thread lifecycle, scheduler, locking/RCU and required atomics |
| Filesystems | VFS, ext4 read/write, initramfs, procfs, sysfs, devtmpfs/tmpfs |
| Networking | Ethernet, ARP, IPv4/IPv6, ICMP, TCP/UDP, loopback and Unix sockets |
| Userspace | ELF64 Linux programs, ordinary init/shell/utilities and ext4/network workloads; exact test-rootfs inputs pinned separately |
| Deployment | Built-in target kernel; module lifecycle tested where explicitly required, no general third-party module ABI promise |

Other hardware drivers, alternate page sizes, 32-bit compatibility, graphics,
wireless, USB, other filesystems/protocols and optional facilities such as eBPF
are out of scope until deliberately added. Exclusions must appear in checked-in
configs and test manifests. Security/isolation behavior of included features
remains part of the contract. This bounds the kernel rewrite, not the later
userspace rewrite; that distribution inventory requires a separate decision.

Completion requires Rust implementation of all code required by those target
configs and passing their declared compatibility/system tests. Inventory any
necessary assembly separately; executing C shims/fallbacks do not disappear from
the count. Report linked code/data contributions by source language with unknown
and linker-generated contributions visible. Byte percentages are a progress
indicator, not a substitute for subsystem or behavior completeness.

### Near-term sequence

- **Phase 1a:** pinned container toolchain, CI, complete Rust BRD on x86_64,
  ordinary userspace performing ext4 I/O, and paired C/Rust tests. Basic lifetime,
  error handling and concurrency correctness are required for the implementation.
- **Phase 1b:** arm64, performance/memory budgets, expanded failure/concurrency
  stress and instrumentation. Bit-identical builds on two independent machines
  are deferred; pinning the container and recording inputs is sufficient now.
- Replace the rebase rehearsal with porting one selected upstream fix into a
  migrated component and demonstrating its regression test.
- Immediately after BRD, scout **`struct completion` ownership and wait/wakeup**
  as a small core boundary: inventory embedded C uses, establish how Rust can own
  state while C still accesses a temporary layout, and test lifetime/ordering.
  This is a candidate to validate, not permission to assume its layout can change.
  Produce an executable spike and a dependency order for reducing the C core
  (synchronization/RCU, task lifecycle/scheduling, page ownership and mm), rather
  than an indefinite sequence of leaf-driver ports.

## Consequences

We accept responsibility for security triage and divergence maintenance instead
of relying on repeated upstream merges. The LTS transition may require importing
newer Rust interfaces or revising their implementation; it is not a documentation
rename. Target expansion and baseline upgrades need explicit decisions and tests.
The tighter target and phases make completion measurable without reducing the
intended end state to Rust drivers on a permanently C kernel.
