## Real callers and contract

- `mm/vma_modify_rust.rs:468` private `modify` calls `rusix_modify_merge`, which delegates to native existing-range merge. That call may free the original VMA; Rust correctly returns without dereferencing it on success. The new implementation must preserve this invalidation boundary.
- `mm/copy_vma_impl.h:146` calls copied-range merge. Its wrapper transfers `middle` to `copied_from`, clears `middle`, and invokes new-range merge. Preserve copy/fork anon ancestry restrictions.
- `mm/vma.c:2881` and `3010` reach new-range merge from mmap/brk paths. `mm/mremap.c:1498` calls extend; `mm/vma_exec.c:58,91` calls expand then shrink around page-table movement. Exec's partial-failure cleanup is not a transaction rollback promise.
- `mm/vma.h:69` declares mutable shared merge state and bitfields. Its contract explicitly permits mutation of any field. Native stack contexts still have C callers, so do not represent them by invented Rust layout or promise stable postfailure context values.
- Require mmap write lock plus per-VMA write acquisition in the original order. No safe Rust references spanning callbacks, lock transitions, retirement or mutable aliasing. Opaque native cursor access remains temporary; maple cursor position is behavioral state, not incidental bookkeeping.
- Existing-range starts within middle, probes next then rewinds, selects previous only when merging left, and resets cursor to original start/load on allocation abort. New-range expects the gap (or previous for `just_expand`). `vma_shrink` preallocates before acquiring VMA write and clearing the range. Preserve each mode separately.
- Matching covers flags ignoring exactly `VM_IGNORE_MERGE`, policy, file identity, uffd context, anon name, pgoff continuity and pairwise anon ancestry. Left+right individual compatibility does not prove left/right compatibility. `VM_SPECIAL` refuses merge; `vm_ops.close` prevents descriptor removal and can reduce a both-side merge to left-only. Merge retirement does not call close, unlike munmap/remove.
- `dup_anon_vma` assigns destination ancestry before native clone and only marks the rollback destination after success. Native `anon_vma_clone` owns failure cleanup (rmap.c). Preserve this ordering rather than introducing unreviewed RAII cleanup. Expansion can duplicate from both removed-next and copied-from; do not collapse those calls or change an early-return path.
- `commit_merge` preallocates maple storage before prepare/range mutation. After that success boundary it cannot return an error. Prepare/complete retain interval lock and publication/free order; THP adjustment precedes range update/store. Sticky flags and khugepaged notification remain after successful commit.
- Existing-range returns NULL for both refusal and allocation failure, distinguishing `VMA_MERGE_ERROR_NOMEM` only unless `give_up_on_oom`. New-range delegates expansion and preserves its state behavior. Use pinned unsigned arithmetic/page units; no saturation, changed errno or enhanced rollback in a translation.

## Making state ownership real

First remove the full native merge-policy calls while preserving exact C-facing contracts. Then, in a separate internal refactor, let Rust own private `MergePlan`/prepared transaction state and call prepare/complete directly from Rust rather than bouncing through C. Explicitly represent target, retained neighbors and consumed removals; after commit only the returned target may be read. Keep native output projection only for remaining mmap/brk/exec callers. Migrate those callers and munmap next, then delete the projection and redundant field accessors. Do not freeze `vma_merge_struct`, `vma_prepare` or `vm_area_struct` layouts as permanent ABI. Actual VMA allocation/layout ownership awaits migration of all direct field users, not just these decisions.

## Why munmap is next, not bundled now

`vms_gather_munmap_vmas` (1434) adds detached maple ownership, split partial effects, sealed mappings, accounting and uffd preparation. `do_vmi_align_munmap` (1619) has a distinct point of no return after clearing the primary tree; failures reattach, but prior successful splits may remain. `vms_complete_munmap_vmas` (1366) may downgrade the mmap lock, clears PTEs/TLB, accounts pages and frees descriptors. `vms_abort_munmap_vmas` (2519) cannot resurrect a mapping after PTE/close cleanup and may deliberately leave a MAP_FIXED gap.

The next complete unit should therefore include init/gather/reattach/clear-PTE/cleanup/complete/abort plus both munmap entries and mmap replacement callers, preserving unlock-on-success and current-mm assumptions. It is materially broader than merge and should follow a proven Rust merge/split transaction. This ordering removes connected C core rather than accumulating isolated helpers or treating adapters as an endpoint.
